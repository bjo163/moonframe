# ADR-0002 — Bounded DTCG token source; generator candidate decision

**Date:** 2026-10-26. **Status:** `maintainer-decision-recorded-for-bounded-format-and-source-layout` / **fixture proof passes; repository runtime is pinned to Node 24.22.1 LTS**. This is not a production generator selection or a claim of DTCG-2025.10 conformance.

## Context and evidence

The repository has 78 example semantic IDs but no approved token values. DTCG 2025.10 is a Final **Community Group** report (not a W3C Recommendation): [Format](https://www.designtokens.org/tr/2025.10/format/), [Color](https://www.designtokens.org/tr/2025.10/color/), [Resolver](https://www.designtokens.org/tr/2025.10/resolver/). The format requires JSON Pointer reference support from conforming tools; this proposal intentionally excludes that feature, so it is a **Moonframe-specific DTCG-inspired subset** and must not be called DTCG-conformant. [Style Dictionary's current DTCG page](https://styledictionary.com/info/dtcg/) still says 2025.10 is not fully supported in v5; a targeted fixture with v5.7.1 is recorded below and does not imply full conformance.

## Recorded decision and bounded subset

1. Adopt a **DTCG-2025.10-inspired bounded source JSON** for *future* authored primitives and roles with `$type`, `$value`, `$description`, optional `$deprecated`, optional `$extensions.moonframe`, and whole-token `{path.to.token}` aliases. The fixture proof currently supports `color` (sRGB object with 3 components and optional alpha), `dimension` (`px|rem`), `duration` (non-negative `ms`), and finite `number`. `fontFamily`, `fontWeight`, `cubicBezier`, and `shadow` remain unsupported pending fixtures. Tokens require an explicit `$type`; group-level type inheritance is not implemented. Reject unsupported constructs rather than silently transform them.
2. Reject group-level `$type` inheritance, `$extends`, `$root` group tokens, JSON Pointer `$ref`, resolver module modifiers, arbitrary gradients, custom CSS code strings, OKLCH source values, unsupported token/group properties, unknown color/dimension/duration value fields, and extension keys other than `$extensions.moonframe`. The proof fails on these constructs instead of silently skipping them. Several are part of upstream 2025.10; excluding them makes this a Moonframe-specific subset, not a conforming implementation. Do not invent extra `$*` keys; Moonframe metadata belongs inside `$extensions.moonframe`.
3. Keep **only one manually-edited future source tree**, as specified by [source plan](../../contracts/moonframe-token-source-plan-v0.1.json), with shared reference/role defaults and sparse per-skin/per-mode patches. Overlays are a **Moonframe pipeline feature**, not a claim that the DTCG specification defines Moonframe inheritance. Validate the completely merged 30 maps before generation.
4. Publish build outputs (resolved maps, CSS custom props, Tailwind bridge, TS token IDs and Skin Lab data) strictly as generated artifacts, never sources of truth. No generation or production files in this phase.

## Alternatives considered

- **Full DTCG 2025.10/Resolver/Color support now:** broader interoperability but unverified tool support and unnecessary complexity; defer.
- **Style Dictionary v5 as mandatory now:** v5.7.1 passes the four proposed token types and alias-output smoke, but its DTCG 2025.10 implementation is not full and does not enforce Moonframe's narrower subset; keep it as a candidate only.
- **Custom tiny generator:** initially more transparent for limited outputs but must own parsing, alias/type/color handling, and future compatibility; the fixture resolver demonstrates only the bounded subset, not a production implementation.
- **30 unrelated CSS files manually edited:** rejected due to duplication/drift and impossible cross-map completeness.

## Trade-offs, confidence, revisit conditions

The [fixture proof v0.1.0](../../scripts/token-subset-proof.mjs) has no third-party package dependency and is run with Node **24.22.1 LTS** via `actions/setup-node` and `.nvmrc`; see the [Node runtime policy](../architecture/node-runtime.md). The proof exercises four types, multi-hop whole-token aliases, self/two-/three-token cycles, missing targets, alias type mismatch and malformed syntax, finite numeric checks, valid group/token metadata, and explicit rejection of unsupported inheritance, references, properties, value-object fields and extension keys rather than silently ignoring them. It also checks required role and mode coverage, byte-deterministic CSS, a runtime `[data-mode]` property bridge, and a Tailwind v4 `@theme inline` alias. `node scripts/token-subset-proof.mjs --emit-css` exposes only the generated CSS for downstream compilation. That CSS compiled in a temporary Tailwind CSS/@tailwindcss-vite 4.3.3 fixture: the generated `bg-mf-canvas` utility resolved to `var(--mf-color-surface-canvas)`, and both `[data-mode=light]` and `[data-mode=dark]` variables remained in output. The external fixture is not a production consumer and is not committed; its package lock remains temporary. A separate temporary Node 24.22.1 fixture pinned `style-dictionary@5.7.1` (npm integrity `sha512-qO9WsyR5jZWz8+5JRtehn7HF8YAvm+Jd8UxiYHtvZhYSNwfMfAVOBK1anjdZwbH+njFb7xuQsjqpD+djPXErcw==`) and generated CSS for color, dimension, duration, number, and whole-token aliases; `outputReferences: true` preserved references as CSS variables. The same processor accepted group `$type` inheritance and a `2vh` dimension, both outside the proposed Moonframe subset, so the strict Moonframe validator must run before Style Dictionary. The [Style Dictionary changelog](https://github.com/style-dictionary/style-dictionary/blob/main/CHANGELOG.md) records 5.7.0 duration support and a 5.7.1 prototype-pollution fix. This establishes targeted compatibility only, not production support or a generator selection; full DTCG 2025.10 support is still explicitly incomplete in the upstream docs.

Confidence: **high** that the bounded fixture algorithm is implementable; **medium/low** on long-term type support, production output and tool choice. Revisit if a pinned tool fully supports the needed format subset, if browser compatibility needs broader output fallback, if a chosen Moon app requires SSR splitting, or if complex tokens become valuable.

## Regression and rollback proposal

The current proof is a standalone validation/generation script with fixture-only values; it is not imported by the Moonframe package and emits no committed production output. If its proposed syntax or resolution rules are rejected, revert the proof and this ADR change together while preserving the prior source-plan and contract history; no consumer migration exists today.

If a production generator is later approved, treat a source schema/alias semantic change as an explicit token-format compatibility change. Generate CSS and TypeScript outputs atomically from canonical sources, keep the negative fixtures as regression cases, and roll back the source, generator and generated outputs as one commit. Never mark any of the 30 production maps complete as part of a generator rollback or proof-only change.

This rollback plan applies to the recorded format decision; no production generator or consumer migration has been exercised.

**Decision boundary:** The maintainer records the bounded Moonframe-specific DTCG-inspired format and selects `tokens/source/**/*.tokens.json` as the future canonical source layout. The repository dictionary remains the authority for token IDs and semantics; current CSS stays the interim runtime implementation. Format/dictionary semantic changes require an explicit format-version change; additive compatible token values may be minor, while ID, type, alias, or semantic changes are breaking. Generator version and package semver must be recorded independently. This does not create token values, select a production generator, authorize generation, or approve any of the 30 skin/mode maps. Extend fixtures and review actual values/contrast before production adoption.
