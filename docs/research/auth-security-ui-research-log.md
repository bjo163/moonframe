### Provider comparisons: constraints, not winner

1. **Auth.js**: suitable candidate for framework-specific session/OAuth and custom pages. Official docs mark WebAuthn experimental and point to Better Auth migration; do not infer organizations/MFA plugin parity.
2. **Better Auth**: self-managed TypeScript framework/plugin ecosystem; organization, 2FA and passkey documented, but plugin behaviors vary by sign-in method and may require DB migrations. SSO deployment/enterprise self-service not automatically included.
3. **Clerk**: hosted/full-stack auth with prebuilt/self-customization, team/org functions; higher vendor/deployment coupling, dashboard policies and plan gates; individual MFA/passkey behaviors depend on instance date/settings.
4. **Supabase Auth**: good candidate for Supabase-backed apps, PKCE/SSR and TOTP; **passkeys experimental** as of research and not evidence of stable Moonframe support.
5. **Firebase Auth**: credible managed email/social sign-in; tenant/enterprise/MFA/passkey/SSO specifics are **unverified here** and require platform SKU/API-level proof.
6. **WorkOS**: enterprise SSO/Directory Sync/AuthKit specialist. Directory synchronization does not automatically imply local session revocation/role sync unless Directory Provisioning is explicitly used.

**Recommendation:** provider-neutral **thin presentation adapter**; do not build a generic authentication framework or install any provider. Evaluate real consumer architecture (existing #1/#4) and chosen services only after a controlled security integration spike.

### Open decisions and triggers

Provider selection depends on actual consumer auth deployment and SSR/BFF routing, tenant/account model, password/session ownership, MFA and required AAL, passkey recovery, SSO/SCIM, license/price quotes and locale support. When undecidable use explicit `unverified` in matrix, not “supported”. No misleading security/accessibility certification.
