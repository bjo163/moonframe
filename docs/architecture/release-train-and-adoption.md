## Release policy and evidence hierarchy

1. Every milestone has a **release decision**. `docs-only checkpoint` means reviewed documentation (no software); `internal preview` means repeatable local consumer artifact; `prerelease` requires package/compatibility tests and owner-approved scope; `release candidate` requires additional evidence; `stable` requires explicit maintainer/legal/security signoff.
2. **No releases/tags/npm publications performed** by this plan; all version strings are proposals. Before package-name availability, scope, license, trademark, CI credentials and publishing privileges are approved, adopt via synthetic consumer/workspace or local `npm pack` tarball only after the respective build supports it.
3. Release notes must include revision/commit, shipped exports, tested browser/Node/React/bundler matrix (only actually tested), known gaps, data/security boundaries, accessibility evidence and rollback/migration instructions. Schema version, contract version and package SemVer are independent.
4. A green `node scripts/validate-contracts.mjs` gate covers documentation/contracts only. Production claims require real builds/tests, assistive-tech/manual reviews, screenshots, provenance and consumer evidence. `15 × light/dark = 30` appearances and `15 choose 2 = 105` skin-pair reviews are required for a **full-skin** claim, not automatically for a carefully scoped early-preview subset; all unreviewed pairs remain `not-reviewed`.
5. Before a release decision, capture a verdict: `release`, `prerelease`, `docs-only checkpoint` or `blocked`, with reviewer name if authorized, links, change notes, blocker and recovery task. Never infer reviewer identity. A blocked milestone is not released.

## Consumer adoption lane & feedback loop

| Checkpoint | Consumer action | Capture as evidence | Abort/revert condition |
|---|---|---|---|
| M0 | Read snapshot and run contract validation on checked-out source | SHA, CI URL, node output, issue links | Wrong ID or broken schema; no package to adopt |
| M1 | Synthetic fixture install via approved workspace/tarball, import public export (not `src/`) | package file list, clean install/build/types, CSS and Node/React versions | Hidden internal import, incompatible peer deps, missing CSS |
| M2–M3 | Fixture tokens/themes through public CSS and resolver entry | Mode/persistence errors, hydration and light/dark assertions | invalid alias/missing token/flicker |
| M4–M6 | Same-content four-skin screens then form/overlays | 8 screenshots, keyboard/focus tests, styling bleed, bundle/import checks | broken semantics, inaccessible interaction or visual regression |
| M7–M8 | Demo pages and optional data workspace against synthetic adapters | Loading/error/empty, query/sort/selection, integration friction | accidental auth/backend coupling or unsafe data handling |
| M9–M10 | Opt into reviewed skins and optional assets only | pair-review ledger, rights/motion/mute evidence | unsupported skin or unlicensed/essential sound |
| M11–M12 | Controlled adopter pilot with version pin | upgrade notes, regressions, security/a11y/manual approval | missing release gate; revert adopter pin |

**Track friction:** CSS import and Tailwind v4 static class detection, SSR hydration, keyboard/a11y, TypeScript paths/peer dependencies, bundle size, style leakage, accessibility regressions, consumer upgrade diffs. Do not invent real Moon ecosystem consumer versions: `synthetic-reference-consumer` is a proposed fixture until real evidence exists.
